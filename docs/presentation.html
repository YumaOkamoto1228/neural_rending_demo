成果報告 / UNITY × ローカル画像生成AI

3Dの映像を、AIでリアルタイムに写実的な映像へ

Unityで作ったシンプルな3Dの村を歩くと、その映像をローカルPCの画像生成AIが写実的に描き直し、Unityの画面に表示するシステムです。改善前は約3秒遅れて表示されていたものを、約0.2秒まで縮め、カメラを動かしたときのちらつきを約6割減らしました。

操作から表示までの遅れ3秒 → 0.2秒
1秒あたりの描き直し枚数12.5 枚
AIの処理時間(1枚)94.7 → 48.1 ms
ちらつき−61 %

何をするシステムか

プレイヤーはUnityの中を歩き回り、AIが描き直した映像を見ながら操作できます。すべて手元のPC(RTX 5070)の中で動きます。

前提となる用語

フレーム / fps映像を構成する1枚1枚の画像がフレーム。1秒あたりに表示できる枚数がfps。
画像生成AI(Stable Diffusion)ランダムな「ノイズ」から少しずつ絵を描き出すAI。元の画像にノイズを足してから描き直すと、元の構図を保ったまま見た目を変えられる。
StreamDiffusion画像生成AIを動画向けに高速に動かす仕組み。複数のフレームの処理を少しずつずらして並行して進める。
TensorRTNVIDIA製の高速化ツール。AIの計算をGPUに最適な形に変換し、同じ結果をより短い時間で出す。
深度カメラから画面の各点までの距離。Unityは3Dの世界を描いているので、正確な値が得られる。
モーションベクトル画面の各点が、前のフレームからどの方向に何ピクセル動いたか。
1 / 経緯と狙い

世界の形は3Dモデルで、見た目はAIで

Google DeepMindの「Genie 3」は、AIが世界そのものを生成し、その中を自由に動き回れる技術です。ただし、1分以上その世界にいると地形や配置が崩れ、来た道を戻っても異なる世界になってしまう(世界が破綻する)という問題があります。

目的は根本的に異なりますが、世界の形はあらかじめ3Dモデルで作っておき、AIには見た目の加工だけを任せる方法を考えました。

  • 世界が破綻しない: 建物の配置や形は3Dモデルが決める
  • 高品質でも容量が小さい: 作り込みの少ない3Dモデルでも、質感はAIが描き足す
  • 低コスト: 近年のAAAゲームなどで問題になっている、容量や制作費の削減につながる

これを、ローカルPCで、操作できる速さで動かすことを目標にしました。

2 / 最初に作った仕組み

リアルタイムで動かすための工夫

flowchart LR
    C[Unity
AI用カメラ 512x512] -- JPEG 1枚=1パケット / UDP --> P[Python
最新の1枚だけ受信]
    P --> AI[StreamDiffusion
img2img + LCM-LoRA + TinyVAE]
    AI -- JPEG / UDP --> R[Unity
画面に表示]

Unityで描いた映像をPythonに送り、AIで描き直してUnityに送り返す構成です。最初の実装の時点で、遅れを減らすために次の工夫をしていました。

工夫内容と理由
UnityとPythonを分ける3Dの描画はUnity、AIはPythonと、それぞれ得意な環境で動かし、同じPCの中で通信する
TCPではなくUDPで通信TCPは届かなかったデータを再送して待つため、遅れが出る。映像は最新の1枚が届けばよいので、待たないUDPを選んだ
1フレームをJPEGで1パケットに収める映像をJPEGに圧縮し、UDPの1回の送信(約64KB)に収めた。分割や再組み立てが不要になる
古いフレームを捨てて最新の1枚だけ処理AIの処理が追いつかないと、届いた映像が溜まって遅れが積み重なる。溜まった分を読み捨て、常に最新の映像だけを処理する
AI用のカメラと解像度を固定画面表示とは別のカメラで512×512の画像を作り、送信は30fpsに固定。AIの入力をいつも同じ大きさ・量にする
StreamDiffusion画像生成AIを動画向けに高速化する仕組み。複数フレームの処理をずらして並行して進める
img2img(元の画像から描き直す)ゼロから描かず、Unityの映像にノイズを足してから描き直すことで、建物の配置を保つ
LCM-LoRA / TinyVAE / 半精度計算通常は数十段階かかる描画を3段階で済ませるLCM-LoRA、軽量な画像変換のTinyVAE、半精度計算で処理を軽くする
CFGを使わない指示文の効きを強める処理(CFG)はAIの計算が倍になるため、使わずに速さを優先した
乱数の固定、避けたい要素の指示を絞るフレームごとに結果がばらつかないようにする
起動時のウォームアップ最初の数フレームが遅くならないよう、映像を受け取る前に空の画像でAIを動かしておく
TensorRTでの高速化(を想定)NVIDIAの高速化ツールでAIの計算を最適化する設定にしていた
3 / 見えてきた課題

動いたが、目標とは離れていた

この仕組みで動かすことはできましたが、操作してから映像が変わるまでに約3秒かかり、画質も低く、カメラを動かすと模様がちらつく状態でした。調べると、次の原因が見つかりました。

課題調べて分かった原因
約3秒の遅れPythonの環境で複数のバージョンのライブラリが混ざって壊れていた。動いていたPyTorch(AIの計算ライブラリ)はRTX 5070に対応していなかった。TensorRTも、必要なライブラリが入っておらず、RTX 50シリーズに対応していない古いバージョンだったため、エラーを出さずに高速化なしで動いていた
画質が低い変化を分かりやすくしようと、汎用のAIモデルへの指示文(レンガの家、黒い屋根)を実際の村(白い壁、わらぶき屋根)と異なるものにしていたことが裏目に出て、品質が落ちていた
カメラを動かすと模様がちらつくAIは毎フレームを独立した1枚として描き直すため、前に描いた模様を覚えていない。AIに与えるノイズが画面に固定されていて、カメラが動くと模様が建物の上を滑る
4 / 改善の取り組み

課題を一つずつ解決する

実行環境を作り直す

RTX 5070に対応したPyTorch(CUDA 12.8版)で、Pythonの環境を一から作り直しました。複数のバージョンが混ざって壊れていた環境を部分的に直すより確実だったためです。

遅れ 3秒 → 0.4秒7.2 fps

処理時間を測って、遅い場所を特定する

受信、AI、表示、送信のそれぞれにかかる時間を1秒ごとに表示するようにしました。AIの処理が全体の約87%を占めていて、ここを速くすべきだと分かりました。

AI 121ms / 1フレーム 約140ms

高速化ツール(TensorRT)をRTX 50シリーズに対応させる

StreamDiffusion付属の高速化コードは古いTensorRT向けで、RTX 50シリーズに必要なTensorRT 10では動きませんでした。コードを取り込んで、削除された命令を新しいものに置き換えるなどの修正をしました。高速化の前後で出力が同じ画像になることも確かめています。

AI 94.7ms → 48.1ms(約2倍速)12.5 fps / 遅れ約0.2秒

写実的なモデルと、シーンに合った指示文にする

3つのAIモデルを同じ画像で比べ、写実系のモデルに変えました。速度はどれも約48msで同じです。指示文が村の見た目とずれていると、奥の家並みが畑に変わるなど建物の形まで崩れることも分かり、指示文を実際のシーンに合わせました。

ちらつきを数値で測る仕組みを作る

村の画像を少しずつ横にずらして「カメラの横移動」を再現し、AIの出力を移動量だけずらして重ねたときの色の差を測るツールを作りました。入力は単純な平行移動なので、理想的な出力なら差は0になります。この数値で、対策の効果を比べられるようにしました。

ノイズを景色に張り付ける

AIはノイズから絵を描きます。ノイズが画面に固定されていると、カメラが動いたときに模様が建物の上を滑ります。そこでノイズを景色と一緒に動かしました。最初の素直な方法では逆にちらつきが23%増えたため、原因を調べました。AIは8×8画素のマス目単位で計算しているので、マス目単位でノイズを動かす方式に直しました。

模様が少しずつ変わる量 −48%

前のフレームの結果と合成する

前のフレームの出力を、動いた分だけずらしてから今の出力と半分ずつ混ぜます。ノイズの移動は「ゆっくりした変化」を、合成は「隣り合うフレームの差」を抑え、役割を分担しています。

ちらつき −61%模様が少しずつ変わる量 −61%

Unityの3D情報から、正確な動きを計算する

Pythonは処理が間に合わないフレームを捨てているため、Unityが出す「1フレーム前からの動き」は使えません。代わりに深度とカメラの位置と向きを送り、処理するフレーム同士の動きをPythonで計算しました。計算した動きは理論値と一致し、実機でも映像から推定した動きとほぼ一致しました(例: 計算 +35.3px、映像から +33.9px)。

止まっているときに画面が変わり続ける問題を直す

カメラの移動量と回転量を表示して調べると、止まっているつもりでもカメラが1フレームに0.031°ずつ回り続けていました。物理演算でプレイヤーの回転が固定されていなかったためです。設定を直し、1ピクセル未満の動きは「静止」として扱うようにしました。

静止中の画面の変化 0

物陰から景色が現れたときの虹色の縞を消す

建物の陰から背景が現れる場面で、虹色の縞が出ていました。手前の板と奥の壁だけの場面で再現すると、建物の端の細い帯のノイズが毎フレームコピーされ、ノイズが横に引き伸ばされていました。深度を使って「前のフレームでは隠れていた部分」を判定し、そこには新しいノイズを割り当てました。

隣り合うマスが同じノイズの割合 86% → 0%

使い勝手を整える

Unityの再生を止めると約3秒でPythonも自動で終了するようにしました。映像を待つ間もウィンドウの処理を続け、「応答なし」にならないようにしています。

5 / 改善後の仕組み

Unityの3D情報も送り、ちらつきを抑える

flowchart LR
    subgraph Unity
        A[カメラ映像] --> S[送信]
        D[深度 64x64] --> S
        M[カメラの位置と向き] --> S
        R[画面に表示]
    end
    subgraph Python
        S -- UDP --> P[最新の1枚を受信]
        P --> F[動きを計算]
        F --> N[ノイズを景色と一緒に動かす]
        P --> AI[画像生成AI
TensorRTで高速化]
        N --> AI
        AI --> B[前のフレームと合成]
        F --> B
    end
    B -- UDP --> R

Unityから映像と一緒に深度とカメラの位置と向きを送り、各点が前に処理したフレームからどれだけ動いたかをPythonで計算します。その動きを使って、AIに与えるノイズを景色と一緒に動かし、描き直した映像を前のフレームの結果と合成します。追加で送るデータは1フレームあたり約8KBです。

理想的な環境でのテスト

一定の速さでカメラを横に動かしたときのAIの出力。画像を平行移動させただけの理想的な条件なので、実際のUnityの映像ではここまでの効果は出ない。

7 / 限界

仕組み上の限界

細部の変化は、今回の仕組みでは修正できません。

AIは毎フレームを1枚ずつ描き直すため、カメラを動かすと細部の見た目は少しずつ変わります。対策で約6割減らしましたが、完全にはなくせません。

今後は、AIが描いた結果を3Dモデルの表面(テクスチャ)に記憶させるなど、仕組みそのものを変えて解決したいと考えています。同じ場所がいつも同じ見た目になります。

試したが採用しなかったこと

前のフレームの結果を引き継ぐ前の出力をAIの描き始めに混ぜる方式。シミュレーションでは上乗せで約2割改善したが、AIの描き変えが雪だるま式に積み重なり、元の村にない建物や石畳が描かれた。弱めると写実性が下がり、実機でも改善を感じられなかった。
近傍クランプゲームの残像対策で使われる手法。残像は減るが安定性も下がり(ちらつき削減 −61% → −52%)、虹色の縞には効果がなかった。
処理段数を減らすAIの描き直しを3段階から2段階にすると速くなるが、画質の低下が目立った。
