## 2. 最初に作った仕組みと工夫

### UnityとPythonを分けた理由
- 画像生成AIの主要なライブラリ(PyTorch、diffusers、StreamDiffusion、TensorRT)はすべてPython向け
- Unityの中でAIを動かす仕組み(Unity Sentisなど)もあるが、Stable Diffusionをリアルタイムで動かせる速さ・対応状況ではない
- 代わりに、プロセス間の通信とJPEGの変換(片道で数ms)が余分にかかる

### TCPではなくUDPを選んだ理由
- TCPは届いたことを確認し、届かなければ再送する。順番どおりに渡すため、1つ遅れると後続も全部待たされる
- 映像は「古いフレームを待つ」より「新しいフレームを使う」ほうが大事
- UDPは確認も再送もしないので待ちが発生しない。同じPC内の通信ではデータもほぼ失われないので、欠点も小さい

### 1フレームをJPEGで1パケットに収める理由
- UDPの1回の送信の上限は65,507バイト。512x512の生データは786KBで1回では送れない
- 分割すると「全部届いたか」の管理が必要になり、1つ失われるとそのフレームが壊れる
- JPEG(画質75)なら30〜50KB程度で、1回の送信 = 1フレームにできる。届けば完全な1枚、届かなければ捨てるだけ
- 返信側は画質60でさらに小さくしている

### 古いフレームを捨てる理由と方法
- Unityは毎秒30枚送るが、AIは毎秒約12枚しか処理できない。全部を順番に処理すると、待ち行列が増え続けて遅れが際限なく大きくなる
- `select()` で「受信待ちのデータがあるか」を待ち時間0で確認し、ある限り読み続けて最後の1枚だけを使う
- 実測では毎秒約18枚を捨てている(ログの `dropped`)

### 512x512・30fpsに固定した理由
- Stable Diffusion 1.5は512x512の画像で学習されていて、この大きさが最も品質が安定する
- TensorRTは入力の形を固定して最適化する(エンジン作成時に形を決める)
- 30fpsに固定するのは、処理できない量を送り続けないため

### StreamDiffusion(Stream Batch)
- 普通は「1枚を3段階で描き終えてから次の1枚」と進める
- StreamDiffusionは「新しいフレームの1段階目」「1つ前のフレームの2段階目」「2つ前のフレームの3段階目」を、まとめて1回のAI計算(3枚同時)で行う。GPUは1枚ずつよりまとめて計算するほうが効率がよい
- 代わりに、出力は入力より2フレーム遅れる(遅れの一部になる)

### img2img と `t_index_list=[25, 40, 45]`
- AIは50段階でノイズを取り除くように学習されている。数字は「50段階のどこから描き始めるか」
- 25から始める = Unityの映像に中くらいのノイズを足し、そこから描き直す
- 数字が小さいほどノイズが多く、大きく描き変える(写実的になるが元の配置から離れる)。大きいほど元の映像に近い

### LCM-LoRA・TinyVAE・半精度計算
- LCM-LoRA: 数十段階かかる描画を1〜4段階で済ませられるよう追加学習した部品
- TinyVAE: AIの内部表現(64x64)と画像(512x512)を変換する部分の軽量版。細部が少し甘くなる代わりに速い
- 半精度(fp16): 数値を16ビットで計算。メモリと計算量が約半分になり、RTXの専用回路(Tensorコア)も使える

### CFGを使わない理由
- CFGは「指示文あり」「なし」の2通りを計算して差を強調し、指示文を効かせる方法。AIの計算量が2倍になる
- LCM-LoRAはCFGなしでも描けるように作られているので、速さを優先して使わない(`guidance_scale=1.0`)

### 乱数の固定とウォームアップ
- 乱数を固定すると、同じ入力から同じ出力が得られ、フレームごとのばらつきが減る
- GPUの最初の数回の計算は準備のために遅い。映像を受け取る前に空の画像で動かしておく

## 3. 見えてきた課題と、その調べ方

| 課題 | 調べ方 | 分かったこと |
|---|---|---|

## 4. 改善の取り組み

### 4-1. 環境の作り直し
- 同じパッケージの別バージョンのファイルが混ざっていて、部分的に直しても不具合が残る危険があった。作り直すほうが確実で早い
- torchは通常の配布元ではなく、CUDA 12.8版の配布元から入れる(RTX 50シリーズに必要)
- StreamDiffusionは `--no-deps` で入れる。依存関係として古いtorchなどを連れてきて上書きするのを防ぐ
- opencvは4.10にする。最新版はnumpy 2を要求するが、diffusers 0.24の環境はnumpy 1.x前提

### 4-2. 処理時間の計測
- 各処理の前後で `time.perf_counter()` を記録し、1秒分の平均を表示(1フレームごとだとばらついて読めない)
- `wait`(Unityからの映像を待った時間)が0なら、Unityは十分速い
- `dropped`(捨てたフレーム数)が多いほど、Python側が遅れの原因
- 当時はAIが121msで、1フレーム全体(約140ms)の約87%

### 4-3. TensorRT 10への対応
- TensorRTは、AIの計算をGPU向けに作り直す(層の統合、GPUに合った計算方法の自動選択、fp16化など)
- 手順: PyTorchのモデル → ONNX(共通形式) → TensorRTエンジン。作成に約3分

| 問題 | 対応 |
|---|---|
| TensorRT 10で、番号で入出力を指定する命令(`get_binding_shape` など)が削除された | 名前で指定する命令(`get_tensor_name`, `set_input_shape` など)に置き換え |
| torch 2.9以降、ONNX変換の標準が新方式(dynamo)になり古いコードと合わない | `dynamo=False` で従来方式を指定 |
| cuda-pythonの新しい版で読み込み方が変わった | 新旧どちらでも動くようにした |
| 毎フレームGPUメモリを確保し直していた | 形が同じなら使い回す |

- 11ではなく10.16を選んだ理由: RTX 50シリーズには10.8以上が必要。11ではさらに古い命令が削除されている可能性があったため、10系の最新にした
- 検証: TensorRTありとなしで出力が同じ画像になることを確認。同じ条件で 94.7ms → 48.1ms
- 注意: エンジンは「モデル x 同時処理枚数(ステップ数)」ごとに作られる。ステップ数を変えると初回だけ作り直し

### 4-4. モデルと指示文
- 3つのモデル(SD1.5, Realistic Vision, DreamShaper)は中身の構造が同じなので、速度は約48msで変わらない。品質だけで選べる
- 使わないセーフティチェッカー(不適切な画像の判定)を読み込まないようにし、ダウンロード量とVRAMを節約

### 4-5. ちらつきの測定方法
- `village.png` を高さ512に縮小し、512x512の窓を1フレームに4pxずつ右へ動かした60枚を作る(カメラが右へ動く状況)
- 入力は単純な平行移動なので、理想的な出力もそのまま平行移動するはず

```
flicker = 平均 | 出力[t] の右側 512-4 列  -  出力[t+1] の左側 512-4 列 |
drift10 = 同じ計算を10フレーム離して行う(ずらす量は40px)
change  = 平均 | 出力 - 対応する入力 |   (AIがどれだけ描き変えたか)
```
(色の差は0〜255の平均)

- flickerとchangeを両方見る理由: AIにほとんど描き変えさせなければ、ちらつきは簡単に減らせるが意味がない。
  そこで「描き変え量あたりのちらつき」(flicker ÷ change)を見た。`t_index_list` を変えてもこれは0.43〜0.50でほぼ一定で、
  パラメータ調整では写実性と安定性を交換しているだけだと分かった
- 限界: 単純な平行移動なので、近い物と遠い物で見かけの動きが違う効果(視差)や物陰は再現できない。最後は必ず実機で確認した

### 4-6. Unityの3D情報を使ったちらつき対策

#### (a) 動きの計算
Unityのモーションベクトルを使わなかった理由: Unityが出すのは「Unityの1フレーム前からの動き」。
Pythonは約3枚に2枚を捨てているので、処理するフレーム同士の動きとは合わない(各画素の動きを足しても正確にならない)。
そこで深度とカメラ行列から直接計算した。

```
1. 深度バッファの値 d → カメラからの距離(DirectXは手前が1、奥が0)
     距離 = near × far / (near + d × (far − near))
2. 画素の位置 → -1〜1 の座標(ndc)
3. カメラ空間の位置:  x = (ndc_x + P[0,2]) × 距離 / P[0,0]   (yも同様、z = −距離)
4. 世界の位置 = 今のカメラ行列の逆行列 × カメラ空間の位置
5. 前のフレームの画面上の位置 = 前の射影行列 × 前のカメラ行列 × 世界の位置 → wで割る
6. 動き(px) = (今の位置 − 前の位置) / 2 × 512   (画像は下向きが正なのでyの符号を反転)
```
- 64x64で計算してから512x512に拡大。追加で送るデータは深度8KBと行列128バイト
- 検証(理論): 10m先の壁の前でカメラを右へ10cm動かすと、理論値は 0.1 ÷ (10 × tan30°) × 256 = 4.43px。計算結果も −4.43px。上への移動、1°の回転も一致
- 検証(実機): 映像から画像処理で推定した全体のずれ(位相相関)と比べて、+35.3px と +33.9px のように一致

#### (b) ノイズを景色に張り付ける
なぜノイズが重要か: img2imgでは「入力 + ノイズ」から絵を描く。描かれる模様はノイズでほぼ決まる。
ノイズが画面に固定されていると、カメラが動いても模様は画面に貼り付いたままになり、建物の上を滑って見える。

| 方式 | 結果 | 原因 |
|---|---|---|
| ① ノイズを補間しながらずらす | +23%(悪化) | 補間すると隣のノイズと混ざり、ノイズの性質が変わる |
| ② 512x512の細かいノイズをずらし、8x8ごとに合計して1/8にする | 4px移動で+4% | 正規分布のノイズ64個の合計÷8は性質が保たれる。それでも0.5マスの半端な位置では隣のマスと混ざり、毎フレーム変わる |
| ③ 各マスが映す世界の座標を追跡し、固定のノイズ表から引く | 1マス(8px)単位の動きで−46% | 採用 |

```
offset(p) = 各マスの「世界の位置 − 画面上の位置」
毎フレーム: offset_new(p) = offset_old(p − 動き(p)) − 動き(p)   (前のフレームで対応していた位置から引き継ぐ)
ノイズ(p) = ノイズ表[ 四捨五入(p + offset(p)) ]   (1024x1024 の固定の乱数表)
```
- ノイズの値は常に乱数表からそのまま取るので、性質が崩れない。1マス未満の動きでは同じ値、1マス動いたら隣の値に切り替わる
- AIの計算の単位(8x8画素 = 1マス)に合わせたのが要点
- StreamDiffusionは3段階を並行して進めるので、各段階のノイズを「その段階で処理しているフレームの位置」に合わせるため、過去のノイズも保持している

#### (c) 前のフレームとの合成
```
出力 = 0.5 × 今のAIの出力 + 0.5 × (前の出力を動いた分だけずらしたもの)
```
- 「今の画素は前のフレームのどこにあったか」を逆にたどって色を取る(`grid_sample`)
- AIの出力は2フレーム遅れるので、2フレーム前の動きを使う
- 動きが64pxを超えたとき、画面外から入ってきた部分、物陰から現れた部分では混ぜない

| | 隣り合うフレームのちらつき | 10フレーム間の変化 |
|---|---|---|
| ノイズの移動のみ | −2% | −48% |
| 合成のみ | −51% | −21% |
| 両方 | −61% | −61% |

ノイズの移動は「模様の決まり方」を揃えるので長い時間での変化に効き、合成は直前と平均をとるので隣り合うフレームの差に効く。
描き変え量は 15.55 → 14.03 と約1割下がる(合成で少し柔らかくなるため)。

### 4-7. 静止中の安定化
- 症状: 止まっていても画面が変わり続けた
- 調べ方: 前後のカメラ行列から移動量と回転量を計算して表示。回転の角度は、2つの向きの差を表す行列Rから `角度 = arccos((Rの対角成分の和 − 1) / 2)`
- 原因: 止まっていても毎フレーム0.031°(毎秒約0.4°)回り続けていた。プレイヤーのRigidbodyのY軸回転が物理演算で自由に動けて、衝突時の回転の勢いが残っていた
- 対策
  1. Rigidbodyの回転を3軸とも固定(Constraints 80 → 112)。向きは `transform.Rotate` で制御しているので物理演算の回転は不要
  2. 画面全体の最大の動きが1px未満なら静止とみなす(デッドゾーン)
  3. 座標がマスの境界をまたいでも、0.75マス離れるまではノイズを切り替えない(ヒステリシス)。0.5を境に行き来して切り替わり続けるのを防ぐ

### 4-8. 物陰の虹色の縞
- 原因: 物陰から現れた部分は、直前にその位置に写っていた「建物の端」の座標を引き継いでいた。
  カメラが動き続けると現れる幅が毎フレーム広がり、端の細い帯のノイズがコピーされ続けて横に引き伸ばされる
- 再現: 手前3mの板と奥10mの壁の場面で、隣り合うマスの86%が同じノイズ値になっていた。AIはランダムなノイズを前提にしているので、縞状のノイズから縞状の色の崩れを描く

```
1. 今の画素の世界の位置を前のカメラに投影 → 前のカメラからの距離 D1
2. 前のフレームの深度画像の、その位置の距離 → D2
3. D1 > D2 × 1.1 + 0.05m なら「前は手前の物に隠れていた」
```
- 隠れていたマスには、ノイズ表の新しい場所を割り当てる(86% → 0%)。合成もしない
- 深度が粗いので、判定した範囲を1マス分広げている
- 誤検出の確認: 地面と壁だけ(物陰なし)の場面でカメラを動かすと、誤判定は0〜1.4%

### 4-9. 自動終了
- 受信を「50msずつ待つ」繰り返しにし、その間もウィンドウの処理(`cv2.waitKey`)を続ける。「応答なし」にならない
- 3秒間映像が届かなければ正常に終了
- 送信用のソケットを分けている。Windowsでは送信先のポートが閉じていると、送信したソケットの次の受信でエラーが返るため

## 5. 改善後の仕組み(データの流れ)

Unityから送るパケット(約40〜60KB):
```
"NRF1" | フレーム番号 | 深度の向きのフラグ | near | far | カメラ行列16個 | 射影行列16個 | 64 | 64 | 深度(半精度) | JPEG
```
- 行列は、深度を描いた時点の値を使う(描画終了時に記録)。映像と行列がずれないようにするため

1フレームの時間の内訳(Unityと同時実行):

| 受信・展開 | 動きの計算 | AI | 表示 | 送信 | 合計 |
|---|---|---|---|---|---|
| 2.3ms | 3ms | 63ms | 6ms | 4ms | 約80ms → 約12.5fps |

- AIが単体(48ms)より遅いのは、UnityとGPUを分け合っているため
- 約0.2秒の遅れの内訳(推定): 処理の約80ms + StreamDiffusionの2フレーム分の遅れ(約160ms) ≈ 0.24秒

## 7. 仕組み上の限界

- AIは1枚の画像を描くように作られていて、前のフレームの記憶を持たない。入力が少し変わると細部の描き方が変わる
- 今回の対策は、描き直しの条件(ノイズ)を揃え、結果を平均して違いを減らしただけ。描き直すこと自体は避けられない
- 前の結果をAIの入力に混ぜる方法も試したが、描き変えが積み重なって元の村から離れてしまい、採用しなかった
- 根本的な解決策
  - AIの結果を3Dモデルの表面(テクスチャ)に焼き付ける。同じ場所はいつも同じ見た目になる
  - 動画用の生成AIを使う(ただし計算が重く、今のPCでのリアルタイム実行は難しい)

## 聞かれそうな質問と答えの例

| 質問 | 答えの例 |
|---|---|
| なぜTCPでなくUDP? | TCPは欠けたデータの再送を待つので遅れが出る。映像は最新の1枚があればよいので待たないUDPにした。同じPC内ではデータもほぼ失われない |
| なぜ毎秒12枚程度? | AIの処理が1枚約50〜60msかかるため。UnityとGPUを分け合っているので単体より遅くなる |
| ステップ数を減らせばもっと速いのでは? | 2段階にすると速くなったが、画質の低下が目立ったので3段階にしている |
| TensorRTで画質は落ちない? | ありとなしで出力が同じ画像になることを確認している |
| Unityのモーションベクトルを使わなかったのは? | Pythonは約3枚に2枚を捨てているので、Unityの1フレームごとの動きは使えない。処理するフレーム同士の動きを深度とカメラ行列から直接計算した |
| 動く物(人や車)がいたら? | 今の動きの計算はカメラの動きだけを考えているので、動く物の部分はずれる。対応するにはUnityのモーションベクトルも送って組み合わせる必要がある |
| 計算が正しいとどう確かめた? | 答えの分かる場面(10m先の壁の前で10cm移動)で理論値と比べ、実機では映像から推定した動きとも比べた |
| ちらつきの数値の意味は? | 平行移動を再現した映像で、AIの出力を動いた分だけずらして重ねたときの色の差の平均(0〜255)。理想的には0 |
| なぜ最初はノイズ対策で悪化した? | AIは8x8画素のマス目単位で計算している。半端な位置にずらすとノイズが混ざって性質が変わるため。マス目単位で動かす方式に直した |
